# Виртуальный тестировщик Motion

Полная сессия раздела Motion в настоящем браузере, без человека перед камерой.

```bash
npm run motion:profile        # раз в неделю: собрать темп людей из motion_log
npm run test:motion-session   # прогон: 7 кругов, ~18 минут
```

Прогон **не стоит в `pre-push`** и стоять там не должен: он идёт восемнадцать
минут, а хук такой длины обходят через `--no-verify` — тем самым обходом, через
который в этот проект однажды уже доехал чёрный экран.

## Зачем

За сессию частота замеров падает с 20 поз/с до 8, задержка показа растёт втрое,
зачёты сыплются с 88% до 68%. Разбор по стадиям в приложении есть
(`src/motion/debug/stageMeter.js`), не было способа получить его, не занимая
живого человека на восемнадцать минут подряд — и не получая каждый раз новый
вход, с которым два прогона не сравнить.

Вопрос у прогона ровно один: **какая стадия конвейера растёт по ходу сессии**.
Если никакая — замедление не в коде.

## Из чего собран персонаж

Ничего не выдумано, всё взято из того, что уже есть в проекте:

| Что | Откуда |
| --- | --- |
| Форма и скорость движений | `src/motion/debug/demoLoops.json` — петли, вырезанные из **живых записей** тем же инструментом, что судит детекторы |
| Какая петля какому движению | `loopKey()` из `debug/DemoSkeleton.jsx` — та же таблица, по которой инструктор показывает движение человеку |
| Темп: повторов за блок, интервал мишеней, время реакции | `prod-profile.json`, собранный из **motion_log с прода** (`prod-stats.mjs`) |
| Расписание сессии | не дублируется вовсе: персонаж смотрит `currentScreen()` и делает то, что просят с экрана |

Повторы в петле считаются по самой записи (`cyclesInLoop`): в звезде их два, и
без этого персонаж делал бы её вдвое чаще человека. Проверка: блок звезды даёт
17–18 повторов за тридцать секунд при медиане прода 17.

## Что в прогоне настоящее

Всё, кроме источника пикселей:

- **браузер** — playwright, окно iPhone 13, настоящая видеокарта (D3D11);
- **сборка** — боевая конфигурация Vite (`vite.harness.config.js` наследует
  `vite.config.js`): та же цель компиляции, тот же `worker.format: 'es'`.
  Проверено: чанк воркера в прогоне и в `npm run build` совпадает по хэшу;
- **код** — тот же `<MotionApp />` из `src/motion`, без единой правки ради прогона;
- **распознавание** — настоящий MediaPipe в настоящем воркере, тот же файл
  модели и тот же движок wasm, что уезжают людям;
- **судейство и отрисовка** — настоящие, по сырым позам от модели.

Готовые позы судье НЕ подаются. Модель распознаёт нарисованного человека
(`figure.js`) из кадра — иначе прогон перепрыгнул бы захват и распознавание, то
есть ровно те стадии, ради которых он и затеян.

## Что подменено и чего это стоит

`camera.js` подменяет **только источник пикселей**: `getUserMedia` отдаёт
заглушку потока, помеченный ей `<video>` отвечает размером кадра, `readyState`
и `requestVideoFrameCallback` по нашим часам, а `createImageBitmap(video)` и
`drawImage(video)` читают холст с нарисованным человеком.

Честные оговорки:

1. **`grab` ниже, чем на телефоне.** Там эта стадия включает декодирование
   кадра камеры, здесь пиксели уже лежат в холсте. На вопрос «что растёт» это не
   влияет — рост ищется в наклоне, — но читать `grab` как абсолютную величину
   нельзя.
2. **Оболочки FitPro вокруг нет** — ни входа в аккаунт, ни навигации. Весь
   конвейер живёт внутри `src/motion`; оболочка добавила бы только вход по паролю.
3. **Движок по умолчанию chromium, а не webkit.** Причина не в удобстве: в
   сборке WebKit, которую везёт playwright, нет `OffscreenCanvas` (проверено
   прямо). MediaPipe по этому признаку уходит на `document.createElement` внутри
   воркера, падает с «Can't find variable: document», и приложение честно
   откатывается считать на главный поток — 2 позы/с и кадр раз в 330 мс. Это
   другая архитектура, и по стадиям такой прогон не читается. Настоящий Safari
   умеет `OffscreenCanvas` с 16.4, и в поле воркер поднимается (`"thread":"worker"`
   в снимках прода). Ограничение харнеса, не продукта; `--engine webkit` остаётся,
   и прогон сам скажет, что считал на главном потоке.

## Зрение персонажа

Экран боя публикует список летящих мишеней — но **только под `?motion-debug`**
(`src/motion/debug/liveTargets.js`). Прогон включает этот ключ сам и сразу
закрывает диагностическую панель, которая иначе легла бы поверх экрана и
рисовала бы собственную разметку каждый кадр.

Цена при выключенной отладке — ноль: решение принимается один раз при загрузке
модуля, вызов в цикле обёрнут в проверку булева значения, а сама
`publishTargets` выходит первой строкой, не прикоснувшись к аргументу. Это не
обещание в комментарии, а тест (`liveTargets.test.js`): список передаётся через
Proxy, который считает каждое обращение — включая `length` и перебор, — и при
выключенном ключе счётчик остаётся нулевым.

Со зрением персонаж не крутит петли в бою, а **тянется** к мишени той стороной,
которая ближе (ловец засчитывает любую), с задержкой и временем выноса из
`reactionMs` прода. Зачёт поднялся с 8% до ~50% при полевых 57%. `--blind`
возвращает слепой перебор — этим сравнивают два прогона.

## Ключи

```
--engine chromium|webkit   движок (по умолчанию chromium)
--tier novice|experienced|pro   уровень (по умолчанию pro)
--seed 7                   зерно персонажа: один seed — один и тот же человек
--limit-min 30             потолок ожидания
--headed                   показать окно
--no-build                 не пересобирать страницу
--extra "block=jack"       короткая проверка: один силовой блок, без сессии
--blind                    без зрения: персонаж бьёт вслепую, как до правки
```

## Что на выходе

Таблица «минута → стадии» (`grab`, `inference`, `judge`, `draw`, `log`) и живые
объекты (мишени, препятствия, частицы, звёзды, узлы DOM, холсты, куча) — рядом,
в одной таблице, чтобы «выросло время» и «выросло число объектов» не пришлось
угадывать из двух разных отчётов.

Время идёт медианой, **число объектов — пиком**. Медиана здесь врала бы: эффекты
попадания живут доли секунды, снимок берётся раз в секунду, и медиана такого
счётчика равна нулю при любом всплеске. Ровно так столбец «частицы» и простоял
в нуле всю двадцатиминутную сессию, пока считался медианой.

Дальше вердикт одного из четырёх видов: нашлась выросшая стадия; частота упала,
а стадии держатся; стадия растёт при держащейся частоте; всё ровно. Полный
отчёт со всеми событиями и журналом — в `reports/motion-session-*.json`.

## Первый запуск

Модель распознавания (5.7 МБ) качается один раз в `tools/.cache/` — прогон
скажет команду, если её нет. `tools/.cache/` в гите не лежит.

`prod-profile.json` собирается `npm run motion:profile` и требует
`VITE_SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` в `.env`. Без него прогон
пойдёт на темпе по умолчанию и честно об этом скажет.
